# Описание механизма кеширования

## Выбор данных для кеша

Критерии: как часто читают, как часто меняют, сколько стоит получить из базы, допустимо ли показывать копию, которая отстаёт от базы на время жизни записи.

| Данные | Читают | Меняют | Стоимость в базе | «Чуть устаревшее» допустимо? | Решение |
|--------|--------|--------|------------------|------------------------------|---------|
| список оборудования | на каждой странице | редко | малая, но запросов очень много | да, плюс инвалидация | кешируем, TTL 60 с |
| карточка оборудования | при открытии | при редактировании | очень малая (строка по ключу) | да, плюс инвалидация | кешируем, TTL 60 с |
| отчёт по статусам | руководитель открывает часто | при любом изменении | большая: `GROUP BY` по всей таблице | да, плюс инвалидация | кешируем, TTL 300 с |
| данные входа (токены, пароли) | при каждом запросе | при входе и выходе | малая | **нет**: отозванный токен не должен работать из кеша | не кешируем |
| результат создания, изменения, удаления | — | — | — | — | не кешируем: запись всегда идёт в базу |

## Ключи и время жизни

| Ключ | Что хранит | TTL | Комментарий |
|------|------------|-----|-------------|
| `equipment:list:v{N}` | массив оборудования | 60 с | в ключ входит номер версии |
| `equipment:item:{id}` | одна единица оборудования | 60 с | номер в ключе: у каждой записи своя |
| `equipment:version` | счётчик версии списков | нет | растёт на 1 при любом изменении оборудования (`INCR`) |
| `report:summary` | сводка по статусам | 300 с | не зависит от параметров |

Все ключи в Redis начинаются с префикса `office:` (его добавляет phpredis: параметр `Redis::OPT_PREFIX`).

## Инвалидация

| Событие | Что делается | Почему |
|---------|--------------|--------|
| создано оборудование | версия `equipment:version` +1; удалён `report:summary` | новая запись может попасть в любой список и меняет отчёт |
| изменено оборудование | то же; удалён `equipment:item:{id}` | устарела и карточка |
| удалено оборудование | то же; удалён `equipment:item:{id}` | не должна отдаваться из кеша |
| истёк TTL | Redis удаляет ключ сам | страховка |

Для списков применена **версия набора ключей**: вариантов запроса бесконечно много, перечислить и удалить их нельзя. Вместо удаления номер версии увеличивается, новые запросы ищут ключи с новой версией (промах, данные берутся из базы), а старые ключи Redis удалит сам по истечении TTL. Цена: до истечения TTL в Redis лежат ненужные ключи старых версий.

## Устойчивость

- подключение к Redis с таймаутом 0,5 с; любые `RedisException` перехватываются;
- после первой неудачи в запросе повторных обращений к Redis нет;
- при недоступном Redis ответ формируется из базы (`X-Cache: BYPASS`), приложение не падает; проверено остановкой контейнера Redis;
- `CACHE_ENABLED=0` отключает кеш целиком.

## Что изменилось в API

| Изменение | Описание |
|-----------|----------|
| `GET /api/equipment`: параметр `limit` (по умолчанию 100) | на 500 тысячах записей ответ «все» невозможен; общее число — в заголовке `X-Total-Count` |
| `GET /api/equipment/summary` | сводка по статусам оборудования |
| заголовок ответа `X-Cache` | `HIT`, `MISS` или `BYPASS` |
| заголовок запроса `X-Cache-Mode: off` | обойти кеш для этого запроса (только при `debug = true`): режим измерений |

## Что проверено

Автотесты (`tests/api-tests.php`, разделы 6 и 7): первый запрос — MISS, второй — HIT; данные из кеша совпадают с данными из базы; кеш не отменяет проверку входа; после `PATCH`, `POST`, `DELETE` данные свежие; отчёт пересчитывается после изменений; обход кеша заголовком. Заодно регрессионные проверки лабораторной работы №9 подтверждают, что кеш нигде не показывает устаревшее.
